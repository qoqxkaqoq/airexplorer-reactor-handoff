# 第二轮接管报告：死循环结论被推翻，真正根因是「重写即破坏」

> 日期：2026-10-22
> 接手基线：HANDOFF.md（第 1 轮）+ 仓库内 7 个 exe + analysis/dep_il.txt
> 结论一句话：**上一轮的「反篡改陷阱体 / 数学死循环」是错误前提；本样本的原版在 Windows 上能正常启动并显示 UI。所有失败都来自「用 dnlib 全量重写文件」这个动作本身。**

## 1. 第一步：先把基准搞对

仓库里没有单独的「原始受保护样本」，但 `exes/AirExplorer_e8runnable.exe` 的 MD5 与厂商官网安装包（`https://www.airexplorer.net/downloads/AirExplorer-OnlineInstaller.exe`，NSIS 内含完整 69 个文件）解出的 `AirExplorer.exe` **完全一致**：

```
a12b5c573e1b54e98cccc29351eaa066  exes/AirExplorer_e8runnable.exe
a12b5c573e1b54e98cccc29351eaa066  <安装包>/AirExplorer.exe
```

即：**原版一直在仓库里**，只是被 HANDOFF 描述成「早期可运行候选（无 UI）」。

原版静态事实（与 HANDOFF 第 2 节的描述不符，需更正）：

| 指标 | HANDOFF 说法 | 实测（原版 v5.11.0.0） |
|---|---|---|
| RVA=0 的方法 | 16586（加密存储） | **7956**，且 100% 是 `Runtime`/`PInvokeImpl`（抽象/外部方法），**没有**一个是加密体 |
| 被掏空的方法 | — | **5808** 个 `nop;nop;nop;ret` 桩（不是 RVA=0，RVA 指向 4 字节桩） |
| 字符串 | 运行时解密 | 原版仅 46 条 `ldstr`，其余走字符串表；`GlobalValidator.FactoryValidator` 资源（398794B，熵 7.999）是加密态，其**已解密形态**就是 `analysis/ExtractorVisitors.bin`（同长度，熵 3.70，长度前缀 UTF-16 串表） |

> `analysis/ExtractorVisitors.bin` 是同长度（398794B）的**解密后**串表，内容形如 `4\0\0\0{{ alg = {0}, type = {1} }}` —— 说明**字符串解密上一轮已经做出来了**，不必再走运行时。

## 2. 死循环之谜：不是陷阱，是「被改坏的体」

### 2.1 dep_il.txt 与落盘体一致

用 `dumpfull` 从 `nb_original.exe` 重新导出 `DefineEfficientProfiler`：

```
导出 9992 指令
diff dep_from_nb.txt analysis/dep_il.txt  →  仅 1 行差异（<PrivateImplementationDetails> 内嵌类型渲染名）
```

结论：`dep_il.txt` **不是**「JIT dump 时刻被反篡改替换的陷阱」，它就是文件里躺着的东西。

### 2.2 但原版里同一方法不是这样

把原版同名方法导出来逐行 diff：**7936 行不同，且差异集中在局部变量编号**：

```
原版    09E5|ldloc|V_27      09EF|stloc|V_72    0A27|ldloc.s|V_90   0A29|ldloc.s|V_9   0A2B|ldloc.s|V_23
nb版    09E5|ldloc|V_104     09EF|stloc|V_104   0A27|ldloc.s|V_104  0A29|ldloc.s|V_104  0A2B|ldloc.s|V_104
```

原版局部变量表是有语义的（`IEnumerator / Byte* / Byte[] / Version / Delegate / 结构体`），nb 版把这些索引**全部塌缩到同两个槽位**——这是工具重写局部变量签名时没有重映射索引造成的破坏。

### 2.3 它不是「逻辑死循环」，是「非法 IL」

Mono 直接给出确定答案（比任何离线模拟都硬）：

```
System.InvalidProgramException: Invalid IL code in
  CloudClient.Templating.DispatcherInitializer:DefineEfficientProfiler (): IL_09EE: add
```

因为 `V_104` 声明的类型不是 `int32`，`add` 在类型检查层就不成立。也就是说：**这个体根本进不了 JIT，谈不上「循环」**。上一轮「V_72 只赋值一次 → 数学必死循环」的推理，是对一份已损坏产物的过度解读。

### 2.4 原版同一方法真的能跑

把原版加载进 Mono 宿主并反射调用 `DefineEfficientProfiler()`：

```
at ...DispatcherInitializer.GenerateConfigurableSpec(string)     ← P/Invoke kernel32!LoadLibrary
at ...DispatcherInitializer.keogyBbmx()
at ...DispatcherInitializer.GenerateAutomatableResponder(...)
at ...DispatcherInitializer.ValidateStaticAuthorizerWatcher(...)
at ...DispatcherInitializer.DefineEfficientProfiler()  [0x0571c]
at <Module>..cctor()
```

它依次做 `LoadLibrary("kernel32.dll")` → `GetProcAddress("OpenProcess")` → `Marshal.GetDelegateForFunctionPointer`，是**反调试**路径，随后才进入真正的解密初始化。停止点只是 Linux 没有 kernel32，不是逻辑错误。

## 3. 真正根因：dnlib 重写 = 必然破坏（对照实验）

这是本轮最关键的一步。我做了 3 个对照，全部在 Windows 2025 runner 上跑（`actions` 真实机器，非仿真）：

| 候选 | 对文件做了什么 | 结果 |
|---|---|---|
| `AirExplorer_baseline_verified.exe`（=原版） | **什么都没做** | ✅ 启动成功，出现主窗口 + 选网盘对话框 |
| `AirExplorer_resave.exe` | **仅** dnlib 读入再写出，逻辑零改动 | ❌ 启动即崩：`InvalidProgramException` @ `VerifyProcessor` |
| `AirExplorer_staticmerge.exe` | 原版骨架 + 5480 个方法体回填 | ❌ 启动即崩：`InvalidProgramException` |
| `AirExplorer_fixinit.exe` | nb_original + 原版初始化体回植 | ❌ 启动即崩：`BadImageFormatException: Bad IL range` |
| `AirExplorer_nb_original.exe` | 上一轮产物 | ❌ 进程存活、**0 个窗口**（复现「无 UI」） |

**「原样 resave 也崩」** 是最有信息量的一条：它排除了「移植逻辑对不对」这个维度，直指文件布局本身。

### 3.1 为什么会这样

原版 `.text` 的熵分布（64KB 块）：

```
.text 偏移 0x000000 ~ 0x620000   熵 ≈ 5.0–5.8   ← IL + 元数据 + 4 字节桩
.text 偏移 0x620000 ~ 0x920000   熵 ≈ 7.997     ← 3.2MB 全熵加密负载
```

节表尺寸对照：

```
AirExplorer.exe (原版)        .text VS=0x927BA4  (9.67MB)
AirExplorer_nb_original.exe   .text VS=0x8E16F4  (9.37MB)  ← 上一轮产物仍保住大部分负载
AirExplorer_staticmerge.exe   .text VS=0x76B1E4  (7.84MB)
AirExplorer_resave.exe        .text VS=0x4D8B14  (5.14MB)  ← 负载被整体丢弃
```

dnlib 只写「它理解的东西」：IL 体 + 元数据 + 资源。`.text` 尾部那 3.2MB 对 dnlib 来说是「方法体之间的空隙」，重写时直接消失。而 Reactor 的运行时初始化正是靠这份负载 + **编译期写死的绝对 RVA 表**去回填方法体：负载没了 / RVA 被重排，回填就写进错误位置，于是 `InvalidProgram` / `Bad IL range`。

这解释了两件一直说不通的事：

1. 为什么「跳过解密」没有 UI —— 解密是必需的，而且解密器依赖负载；
2. 为什么 126 轮里「改得越精细越失败」—— 失败与改动内容无关，**只要经过 dnlib 写出就注定失败**。

### 4.3 执行验证台（本轮真正的解锁点）

上一轮只有「CI 跑进程 → 看有没有窗口」，没有任何异常信息。本轮补了三条通路：

1. **Linux/Mono 执行台**：`monoprep` 剥离特性后，`mono harness/h.exe <exe> <Type> <Method>` 可直接反射调用任意方法并拿到完整托管堆栈 —— 不用 Windows 就能验证初始化链（本轮 2.3/2.4 的结论即来自此）。
2. **Windows 探针** `tools/ci/probe.ps1`：启动 exe → 枚举窗口（标题/类名/可见性/矩形）→ `PrintWindow` 截图（含关闭模态框后再抓主窗口）→ 采 `.NET Runtime` 崩溃事件。
3. **受控宿主** `tools/ci/host.exe`（`host.cs`）：把 exe 当库加载并调用入口点，**打印完整异常链**（`TypeInitializationException → InvalidProgramException → 具体方法名`）。上一轮 126 轮缺的就是这一条。

配套工作流 `.github/workflows/ui-probe.yml`：`workflow_dispatch` 传候选路径即可，产物自动提交到 `ci-<run_id>` 分支（因为制品下载链路的鉴权在该网络环境下不可用）。

## 5. 下一步建议（按性价比排序）

### A. 如果目标是「拿到能跑的 AirExplorer」
**直接用 `AirExplorer_baseline_verified.exe`**（即原版）。它在干净 Windows 上已验证可启动并显示 UI。若用户环境仍无窗口，需要的是**环境侧证据**（崩溃事件日志 / 是否被杀软拦截 / 是否缺 WebView2 运行时），而不是继续改二进制。

### B. 如果目标真的是「静态去混淆且仍可运行」
必须放弃「dnlib 全量重写」这条路，改成**布局保持型**改造：

1. 保留原文件全部字节（尤其 `.text` 尾部 3.2MB 负载）与所有 RVA 不变；
2. 新增节放在文件末尾，恢复出来的方法体写进新节；
3. **原地**改写 MethodDef 表的 RVA 列（4 字节定点写，不动表结构）；
4. 局部变量签名是硬约束：`StandAloneSig` 需要新增行 → 会动 `#~`/`#Blob` → 又会改布局。
   规避方案：先解析出负载里的 `token → (offset, length, key)` 表，**离线解密后按原 RVA 覆写等长数据**，完全不新增元数据。
5. 验证方式：`tools/ci/probe.ps1` + `host.exe` 已就绪，每轮都能拿到具体崩溃方法名。

### C. 反调试/完整性
`DefineEfficientProfiler` 会 `LoadLibrary(kernel32)` → `GetProcAddress("OpenProcess")` 并 `GetDelegateForFunctionPointer` 调用，属反调试探测；同时 Reactor 极可能对镜像做完整性校验。任何改造都要评估这两点，且在 `OpenProcess` 前后打点（探针已支持）。

### D. 建议立刻补的仓库卫生
- `exes/` 已 60MB+，建议把大文件挪到 Release 资产；
- `HANDOFF.md` 第 2/4/6 节的核心前提需按本报告更正（已在文首加指引）。

详见 [`复验_qoqxkaqoq1_v84b_不通过.md`](复验_qoqxkaqoq1_v84b_不通过.md)。
